# 起動と画面表示

## 変更

- PWA起動URLは公開の `public/launch.html`。Relay、部署確認中、見出し、カテゴリ、下部ナビ、骨格を先に表示します。氏名・部署名・role・投稿は含みません。
- Service Worker v2はこのHTMLと専用CSS/JSを事前保存。旧インストールの `/app` 起動も、クエリがない文書ナビゲーションに限り同じ公開HTMLを返します。
- 起動用JSは外枠を描画後、`/app?__relay_start=1` に置き換えます。この認証付きページは毎回ネットワークで取得します。起動用ページ自身は認証proxyを通しませんが、実際の `/app`、`/admin`、各操作の認証・停止・所属・role確認は維持します。
- ホームは投稿と重要連絡を独立したSuspenseでStreaming。重要連絡の遅延が投稿を止めません。認証中の外枠にもカテゴリ・下部ナビを表示します。
- 管理トップはサーバー権限確認後にメニューを表示し、参加申請件数を別のSuspenseで取得します。
- session/DBクライアントは既存のReact cacheでリクエスト内だけ共有。profileとmembershipは並列、部署はmembershipのJOINで取得。長期保存・権限確認の省略はありません。
- Next Linkの自動prefetch・即時押下表示、各ルートのloading.tsxを維持します。読み込み中にもページ名を表示します。

## Supabaseの作業

`202610050003_feed_performance.sql` 適用後に、SQL Editorで `supabase/migrations/202610050004_startup_feed.sql` を一度実行してください。

ホームの各カテゴリを初回30件から15件に減らします。カテゴリの即時切替は維持し、続きは「さらに表示」で30件ずつ取得します。既存migrationは変更していません。新しいindexは追加せず、003の部署・状態・投稿日時・関与者のindexを使用します。

004未適用でもアプリは動きますが、初回は従来の30件です。003も未適用なら互換処理は全件取得になるため、まず003を適用してください。新しいキー・Auth設定は不要です。

## 計測と限界

`node scripts/benchmark-feeds.mjs` は実際のmigrationをローカルPGliteに適用し、同部署1,200投稿の同一fixtureでホーム各30件と15件を比較します。SQL時間・返却サイズを出力します。実SupabaseのEXPLAIN ANALYZEやVercel/iOS実機計測ではありません。

`RELAY_PERFORMANCE_LOGS=1` の場合、サーバーに `proxy.auth`、`session.auth/profile/membership`、`home.feed/notices`、`page.home.posts`、`page.admin` 等の経過時間を出します。個人情報・引数・結果・URLは出しません。`page.admin` は権限確認とメニューまでの時間、件数取得は `admin.admin_dashboard` の時間です。普段は0に戻してください。

キャッシュ済み起動用HTMLを返す処理はテストでネットワーク0件を確認しています。実機の描画速度や通信時間の改善率は未計測です。初回インストールはキャッシュ準備が必要です。起動用HTMLから実際のホームへ文書遷移するため、回線が遅いとデータの待ち時間自体は残ります。

## iPhone / iPadでの確認

1. 修正を含むDeploymentがReadyになったら、一度オンラインでRelayを開きます。
2. 同じRelayを開いているPWAとSafariタブを閉じ、再度起動します。旧workerを使用中の場合はもう一度閉じて開きます。
3. 起動直後に見出し・カテゴリ・下部ナビ・骨格が出て、その後部署名・投稿が入ることを確認します。
4. ホーム→投稿・履歴・マイページ・管理で、押下表示とページ名付き骨格がすぐ出ることを確認します。
5. カテゴリを切り替え、「さらに表示」で続きを取得できることを確認します。管理ではメニューが申請件数より先に表示できます。
6. ログアウト後はログイン画面へ戻ること、一般userは `/admin` を開けないことを確認します。機内モードでは公開の外枠と接続案内だけが表示され、投稿・部署名は残りません。

同じWi-Fiで、完全終了から骨格まで／投稿までをそれぞれ数回計って比較してください。新しいManifestの起動URLが反映されなくても、v2のworkerが有効なら旧 `/app` 起動を処理します。

今回のローカル比較（各3回平均）では、ホームは150件・58,052bytes・22msから75件・29,342bytes・11msになりました。転送対象は約49%減、ローカルSQL時間は約50%減です。件数・時間はfixtureと実行環境によって変わります。実機で同率になるという意味ではありません。
