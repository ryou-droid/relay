# 管理者機能の設定と確認

## Supabaseで必要な操作

アプリは公開用Supabaseキーと本人のAuth Cookieだけを使います。追加キー・service_role・secret key・Auth設定変更は不要です。**新しいSQLの適用だけは必要**です。本作業では実プロジェクトを変更していません。

1. SupabaseのSQL Editorで `supabase/migrations/202610050001_admin.sql` を実行します。既存の001・002を適用済みであることが前提です。初めて構築する場合は001 → 002 → 管理SQL → `202610050002_admin_read_only.sql` の順です。管理SQLが適用済みの場合もread_only修正SQLだけを追加適用してください。
2. 同一組織に同名の部署がある場合、適用はロールバックされます。下の確認SQLで重複・前後空白を見つけ、信頼できる運用者が部署名を整理してから再実行してください。自動削除・自動統合はしません。
3. 最初の組織管理者が未設定なら、登録・メール確認・正式所属を済ませたユーザーに `supabase/setup/first-admin.sql` を適用します。ファイル内の **メールと組織UUIDを自分のものへ変更**してください。テスト組織の場合、先に `supabase/setup/test-membership.sql` を使用できます。既に組織管理者がいるならこの操作は不要です。
4. 必要なら既存の別ユーザーを `/admin/users` から部署管理者へ変更します。自身の権限・利用状態は変更できません。

```sql
-- 部署名の重複・前後空白の事前確認（読み取り専用）
select organization_id, lower(btrim(name)) as normalized_name, count(*)
from public.departments group by organization_id, lower(btrim(name)) having count(*) > 1;
select id, organization_id, name from public.departments where name <> btrim(name);
```

## 組織を混ぜずに申請を受け取る

これまでの未所属profilesには申請先の組織がありません。組織名や希望部署名だけを使って所属先を推測したり、全ユーザーを管理者に公開したりはしません。

- 管理者は `/admin/users` の「参加用の招待コード」を開いてコードを作り、表示される登録リンクを相手に渡します。コードはランダムUUIDで30日間有効。無効化できます。
- 新しいユーザーはリンクから登録すると、コードで確定した組織へ参加申請されます。メール確認後、承認できます。**招待コードだけでは閲覧権限・roleは付与されません。**
- 既存の参加待ちユーザーは `/waiting` で同じコードを入力して参加申請します。希望部署は参考情報であり、正式部署は管理者が選択します。
- 組織管理者は組織全体向けコード、または部署限定コードを作成できます。部署管理者は自部署限定コードだけ作成できます。
- 組織全体向け申請は組織管理者のみ閲覧・承認できます。部署管理者に承認を任せる場合は**対象部署のコード**を渡してください。部署管理者は他部署へ振り分けられません。
- 有効な招待コードを持たない既存の未所属アカウントは、どの組織の承認一覧にも表示しません。招待リンクは必要な相手だけに共有してください。
- 未確認メール・使用済み申請・無効部署・停止ユーザーの承認はDBで拒否します。1ユーザーにつき承認待ちは1件、active所属も1件です。

## URLと操作範囲

| URL | 内容 |
| --- | --- |
| `/app` | 通常のホーム（管理者も利用可能） |
| `/app/posts/new`、`/app/posts/[id]` | 投稿と詳細 |
| `/app/history`、`/app/me` | 履歴とマイページ |
| `/admin` | 管理メニュー |
| `/admin/approvals`、`/admin/approvals/[id]` | 承認待ちと部署選択 |
| `/admin/users` | 招待・ユーザーの所属/権限/利用状態 |
| `/admin/departments` | 部署の追加・名前変更・無効化（組織管理者のみ） |
| `/admin/notices` | 組織または部署の重要連絡 |
| `/waiting`、`/suspended` | 参加待ち・利用停止の専用画面 |

旧 `/` は `/app` へ、旧 `/posts/...`・`/history`・`/me` も対応する通常URLへリダイレクトします。既存PWAのid・scopeは維持し、新規起動先を `/app` にしました。

| role | 通常画面 | 管理範囲 |
| --- | --- | --- |
| user | 自部署の投稿・確認・対応・補足・履歴 | 管理メニューなし。管理URLは `/app` へ |
| department_admin | 自部署の通常利用 | 自部署宛て申請、自部署一般ユーザーの停止/再開、自部署のお知らせ |
| organization_admin | 自部署の通常利用 | 所属組織全体の申請/ユーザー、部署追加/変更、権限/部署変更、組織/部署のお知らせ |

部署管理者による管理者アカウントの変更、roleの変更、部署作成、他部署への異動はできません。本人の停止・権限変更は禁止しています。利用停止はprofilesのsuspendedで判定し、既存Authセッションが残っていても組織データとRPC操作を遮断します。停止ユーザーの再開は管理者が行います。無効化は所属ユーザーのいない部署に限り、物理削除はしません。

通常投稿の閲覧範囲は引き続き**同じ部署のみ**です。組織管理者でも通常画面から別部署の投稿は読めません。管理用メール・プロフィール情報は、権限付きRPCが範囲を確認して返します。一般ユーザーのプロフィールSELECTは本人限定のままです。

## 権限とDB

各管理ページ・レイアウト・Server Actionで `adminSession()` がAuth本人と最新の所属/role/停止/部署有効状態を確認します。レイアウトだけに依存せず、個別ページも確認します。`/admin/departments` は組織管理者を要求します。クライアントから送られたroleや組織IDは本人の権限として使いません。

新しい `organization_invitations`・`join_requests`・`admin_activity_logs` はRLSを有効化。一般ユーザーには自分の参加申請だけ、管理者には組織/部署の管理範囲だけSELECTを許可します。既存departments/membershipsには管理者の範囲付きSELECTを追加。テーブルへのINSERT/UPDATE/DELETEは従来通りクライアントに許可せず、権限確認付きRPCで変更します。内部ヘルパーとAuthトリガーはAPIロールにEXECUTEを与えません。

承認は申請・ユーザー・部署をロックし、メール確認・同一組織・部署権限を検証してから、一般ユーザーroleで正式所属を作成します。権限変更・停止、部署変更、お知らせなどは専用監査ログを残します。名前の重複はDBのunique indexで防止します。

## iPhoneでの確認

1. SQLと最初の管理者設定を済ませ、修正を含むVercel版がReadyになったら管理者でログインします。`/app` の「管理」から `/admin` へ入ります。
2. 「部署」で総務・営業などを追加します。同名追加が拒否されることも確認します。
3. 「ユーザー」で招待リンクを作り、別のテストユーザーへ渡します。そのユーザーを登録・メール確認します。既存の参加待ちユーザーならコードを入力します。
4. 「承認待ち」で **①ユーザーカード → ②縦一覧の部署 → ③承認する**。未選択ではボタンが無効、選択後は青枠とチェックが表示されることを確認します。
5. 承認された一般ユーザーでログインし、`/app` から投稿・既読・状態・補足・履歴を確認します。「管理」が出ないことと、`/admin`・`/admin/users`・`/admin/departments` を直接開いても `/app` に戻ることを確認します。
6. 組織管理者が別の一般ユーザーを部署管理者にし、そのユーザーで自部署限定の招待・承認・停止・お知らせを確認します。他部署の申請/ユーザーが見えず、部署管理URLも拒否されることを確認します。
7. 停止したユーザーが、以前のログイン状態のままでも利用停止画面になり、投稿URLを直接開けないことを確認します。再開後は通常利用できます。
8. 別組織のテスト管理者でも、他組織の申請・ユーザー・部署・お知らせを見られないことを確認します。

メール確認・パスワード再設定のURLは維持しています。再設定リンクは引き続き送信に使用した同じブラウザで開いてください。PWAの静的キャッシュに管理者データは保存しません。

DB権限は実マイグレーションを適用したPGliteで検証しています。実SupabaseへのSQL適用、実Vercel/実機での確認、本番デプロイ操作は本作業からは行っていません。

管理画面の読み込み失敗・安全なログの確認は [25006の修正手順](admin-troubleshooting.md) を参照してください。
